# Planet Resolutions (Part 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a generated planet exist at several 2:1 resolutions side by side, generate a missing one on demand from its stored parameters, switch between them from chips under the planet view, delete added ones, and remember the displayed one per planet on the server.

**Architecture:** Every resolution of a body, the original included, lives in `bodies/<body>/sizes/<W>x<H>/` (same file set as today's body directory), with `thumb.png` beside `sizes/`. The disk is the source of truth for which sizes exist; the index stores the displayed size. A new job kind generates one size of one body with `world_params(body)` and only `width`/`height` changed. Every server route and viewer URL that reads a body's files gains the size; it defaults to the displayed size.

**Tech Stack:** Rust (crates/mapgen, crates/cli, crates/server: axum, rusqlite, ts-rs), TypeScript/Svelte 5 (web/), vitest.

**Spec:** `docs/superpowers/specs/2026-11-08-planet-resolutions-design.md` (part 2, reduce a system, gets its own plan).

## Global Constraints

- 2:1 sizes only: presets 1024×512, 2048×1024, 4096×2048, 8192×4096; default 2048×1024 (was 1920×1080).
- `DEFAULT_MAX_PIXELS` = 8192 × 4096 = 33 554 432 (the doc comment at `app.rs:68-73` already measures 2.0 GiB at that size; `compose.yaml:40` already sets it).
- No compatibility with existing data: no migration code; old `system.json` is refused by `SYSTEM_FORMAT_VERSION`, an index file of another layout is set aside and rebuilt.
- Version bumps (agree the numbers with the peer sessions before Task 3, per CLAUDE.md): `SYSTEM_FORMAT_VERSION` 1 → 2, index `SCHEMA_VERSION` 2 → 3. `FORMAT_VERSION` (raw_data) is unchanged.
- The original size of a body is `body.params.width/height` in `system.json`; it can never be deleted.
- Size names on disk and in URLs: `<W>x<H>`, lowercase `x`, decimal, no leading zeros (`2048x1024`).
- Never write to the main checkout's `systems/`, `worlds/`, `db/`; tests use temp dirs.
- Shared machine: `RAYON_NUM_THREADS=4 cargo test -j 4 --workspace --all-features -- --test-threads=3`, one full run at a time; lint `cargo clippy -j 4 --workspace --all-targets --all-features -- -D warnings`; web `cd web && npm run check && npx vitest run`; never `npm ci` in a worktree; never port 3000.
- ts-rs bindings in `web/src/lib/api/types` are regenerated by `cargo test --all-features` and committed (CI diffs them).
- Docs in the same change as the behaviour: `README.md` (CLI table, file tree, API routes, defaults), the route table at the top of `crates/server/src/app.rs`, `web/README.md` where it describes the viewer, `docs/analysis/15-storage.md` (new "Resolutions" section). No changelog in the repo.
- Commits: Conventional Commits; the PR says `Refs #328` (part 2 shares the eviction path).

## Review Focus

1. **Two clicks on the same missing size** (double click, two tabs): one job, both callers get the same `job_id`. Test in Task 5.
2. **Deleting the displayed size** (from another tab): the displayed size falls back to the original, and the viewer of the first tab reloads the original instead of 404-ing on tiles. Server test in Task 5; viewer behaviour in Task 7 (a 404 on `sizes` reload falls back).
3. **Tile cache with two sizes of one body:** opening 4096 then 2048 must not serve 4096 tiles for 2048 (cache key carries the size) nor evict each other's entry forever. Test in Task 4.
4. **A size over `max_pixels` or `MAX_SIZE`** (a server started with a lower `MAPGEN_MAX_PIXELS`): POST answers 400 `TooManyPixels`; the chip is disabled with the reason. Tests in Tasks 5 and 7.
5. **A crashed size generation** leaves `sizes/.tmp-<W>x<H>`: it is never listed as a size and is swept at start. Test in Task 3.
